# 아키텍처 분석: `encoder.html` (고속) vs. `hq_encoder.html` (사전 확장)

이 문서는 고도로 최적화된 `encoder.html`과 대안적인 `hq_encoder.html` 구현 간의 상세한 비교 분석을 제공합니다.

근본적인 차이점은 **공간적 다운스케일링(크기 축소)이 발생하는 위치**에 있습니다 (1080p/4K 대형 비디오를 MSX 256x192 해상도로 축소하는 과정).

*   **`encoder.html` ("선 다운스케일링"):** 픽셀을 추출하기 전에 브라우저의 GPU가 이미지의 크롭, 패딩 *및* 다운스케일링을 동시에 수행하도록 강제합니다.
*   **`hq_encoder.html` ("사전 확장"):** 브라우저를 사용하여 *원본 고해상도* 상태에서 이미지를 크롭 및 패딩한 다음, 그 거대한 고해상도 프레임을 WASM(Rust) 모듈로 전송하여 CPU가 소프트웨어적으로 다운스케일링을 수행하도록 강제합니다.

## 📊 상세 비교 매트릭스

| 지표 | `encoder.html` (최적화된 Canvas) | `hq_encoder.html` (사전 확장) | 영향 / 차이점 |
| :--- | :--- | :--- | :--- |
| **다운스케일링 엔진** | 브라우저 네이티브 C++ / GPU (`drawImage` 사용) | WebAssembly / Rust CPU (소프트웨어 보간법) | 네이티브 GPU 스케일링이 기하급수적으로 빠르며, 종종 더 우수한 필터링 알고리즘(Lanczos)을 사용합니다. |
| **페이로드 크기**<br>(프레임당) | **196 KB 고정**<br>($256 \times 192 \times 4$ 바이트) | **거대하고 가변적**<br>예: 1440x1080 크롭 시 약 6.2 MB, 1080p 패딩 시 약 8.8 MB. | `hq_encoder`는 스레드 경계를 넘어 최대 **45배 더 많은 데이터**를 밀어 넣어 IPC(프로세스 간 통신)에 심각한 병목 현상을 일으킵니다. |
| **효율성 및 GC**<br>(가비지 컬렉션) | **고효율.** 15fps에서 초당 약 3MB의 메모리를 할당합니다. | **저효율.** 15fps에서 초당 약 90MB ~ 130MB의 거대한 `Uint8Array` 객체를 할당합니다. | `hq_encoder`는 심각한 "stop-the-world" 가비지 컬렉션 스래싱을 유발하여 UI 멈춤과 높은 RAM 사용량을 초래합니다. |
| **WASM 작업량** | **100% 스펙트럼.** WASM은 K-Means 양자화 및 디더링을 수행하기 위해 49k 픽셀만 순회합니다. | **공간적 + 스펙트럼.** WASM은 이미지를 축소하기 위해 먼저 수백만 픽셀을 순회한 *다음* 양자화를 수행해야 합니다. | `hq_encoder`는 실제 MSX 변환을 수행하기 전에 수신한 픽셀의 90%를 버리는 데 막대한 CPU 사이클을 낭비합니다. |
| **이미지 사전 처리**<br>(비율 로직) | Canvas가 수학적 스케일링 오프셋을 사용하여 원본 비디오를 $256 \times 192$ 뷰포트로 직접 스케일링합니다. | Canvas가 거대한 동적 크기의 버퍼(예: 패딩용 $1920 \times 1152$)를 생성하여 고해상도에서 레이아웃을 미리 배열합니다. | `hq_encoder`는 불필요하게 큰 오프스크린 캔버스를 생성하여 데이터 추출 전 브라우저에서 추가 VRAM을 소비합니다. |

## 🔬 심층 분석

### 1. 페이로드 병목 현상 (`hq_encoder.html`)
`hq_encoder.html`에서 코드는 원본 비디오를 기반으로 거대한 경계 상자를 계산합니다. 예를 들어, 표준 1080p 비디오(1920x1080)를 5:3 비율로 패딩하는 경우 `drawW` 1920 및 `drawH` 1152를 생성합니다.
모든 220만 픽셀을 추출(`getImageData`)하고 8.8MB 배열로 직렬화하여 Worker에 게시합니다. 이 직렬화 오버헤드만으로도 인코딩 파이프라인 속도가 크게 저하됩니다.

### 2. "HQ"(고품질) 이론
왜 `hq_encoder.html` 방식을 선호할 수 있을까요?
*   **이론:** 원본 1080p 프레임의 압축되지 않은 고주파수 세부 정보를 Rust 모듈에 전달하면, 이미지가 물리적으로 축소되기 전에 K-Means 색상 양자화기가 전역 팔레트를 더 잘 결정할 수 있다는 이론적 주장이 있습니다.
*   **현실:** 표준 비디오 처리 파이프라인에서 색상 양자화 및 디더링은 공간적 다운스케일링 *이후*에 발생합니다. 또한, 브라우저의 네이티브 `imageSmoothingQuality = 'high'` 구현(`encoder.html`에서 사용)은 일반적으로 축소 시 세부 정보를 보존하는 데 탁월한 Lanczos 컨볼루션 필터를 사용합니다. Rust WASM 모듈이 상당히 우수하고 비용이 많이 드는 소프트웨어 스케일링 알고리즘을 구현하지 않는 한, 시각적 품질 차이는 미미하거나 `hq_encoder` 버전에서 오히려 더 나빠질 수 있습니다.

### 3. 모니터 디스플레이 차이
`hq_encoder.html`에서는 오프스크린 캔버스가 거대하기(예: 1920x1152) 때문에, 사용자 프리뷰를 위해 다시 축소하도록 모니터 렌더링 로직을 업데이트해야 했습니다.
```javascript
// hq_encoder.html은 UI를 위해 거대한 캔버스를 256x192로 다시 축소해야 합니다.
ctx.drawImage(offscreenCanvas, 0, 0, drawW, drawH, 0, 0, 256, 192); 
```
반면 `encoder.html`은 이미 완벽한 256x192 버퍼를 화면에 직접 복사하기만 하면 됩니다.
```javascript
// encoder.html은 단순히 1대1 버퍼를 복사합니다.
ctx.drawImage(video, 0, 0, 256, 192); 
```

## 🎯 결론
`encoder.html`은 웹 기반 도구를 위한 확실히 우수한 아키텍처입니다. 브라우저의 하드웨어 가속 Canvas API에 공간적 조작(스케일링)을 위임함으로써 스레드 페이로드를 아주 작게 유지하고, WebAssembly 모듈이 최대 효율로 작동하여 MSX2 아키텍처에 필요한 복잡한 색상 수학에만 집중할 수 있도록 합니다. `hq_encoder.html`은 시각적 품질 이득이 의심스러운 반면 심각한 성능 및 메모리 병목 현상에 시달릴 것입니다.

## 🧐 추록: 진지한 하드웨어 현실 점검

거대한 L2/L3 캐시, AVX-512 벡터 명령어, 60-100GB/s의 대역폭을 자랑하는 DDR5 메모리 버스를 갖춘 최신 하드웨어를 기준으로 이 아키텍처를 평가할 때, 기존의 "웹 성능"과 관련된 일부 주장들은 좀 더 진지하고 솔직하게 재평가될 필요가 있습니다.

### 1. "페이로드 병목 현상"의 신화 (IPC 및 메모리)
초기 분석에서 `hq_encoder.html`은 WebWorker 경계를 넘어 초당 15회 8MB 배열을 할당하고 전달한다는 점(약 120MB/s) 때문에 심한 감점을 받았습니다.

**솔직한 현실:** 최신 시스템에서 120MB/s의 메모리 할당 및 복사는 오차 범위 수준에 불과합니다. DDR5 RAM 버스는 그 전체 페이로드를 약 1~2밀리초 안에 전송할 수 있습니다. V8 엔진의 최신 동시성 가비지 컬렉터(Concurrent Garbage Collector)는 메인 스레드를 일시 정지하지 않고도 이러한 수명이 짧은 객체들을 매우 훌륭하게 청소합니다. 8MB 전송은 최신 CPU(Apple M 시리즈나 AMD Ryzen 등)에 결코 치명적인 병목 현상이 아닙니다.

### 2. 진짜 병목 현상: PCIe 버스와 GPU 동기화 지점
최신 CPU가 8MB를 순식간에 처리할 수 있다면, 왜 `hq_encoder.html` 방식이 여전히 근본적으로 더 느릴까요? 그 해답은 브라우저의 그래픽 파이프라인 아키텍처와 **PCIe 버스**에 있습니다.

다음 코드 라인을 살펴보겠습니다: `const frameData = offCtx.getImageData(0, 0, drawW, drawH);`

1.  **`drawImage`는 비동기적이며 GPU 가속을 받습니다:** 브라우저는 크롭/패딩 명령을 (Metal, Vulkan 등을 통해) GPU로 푸시합니다.
2.  **`getImageData`는 동기적이며 CPU 바운드입니다:** 이 함수는 거대한 파이프라인 정체(Stall)를 강제합니다. CPU는 GPU에게 렌더링을 멈추고 현재 대기열을 마친 뒤, 압축되지 않은 원시 픽셀 데이터를 PCIe 버스를 통해 시스템 RAM(CPU)으로 다시 보내라고 명령해야만 합니다.

**이 지점이 바로 `hq_encoder.html`이 참패하는 곳입니다.** 8MB(1080p)의 압축되지 않은 텍스처를 VRAM(GPU)에서 시스템 RAM(CPU)으로 PCIe 버스를 통해 읽어오는 작업은 웹 개발에서 악명 높을 정도로 가장 느리고 비용이 많이 드는 작업 중 하나입니다.

`encoder.html`(사전 캔버스 리사이즈) 방식이 훌륭한 이유는, 이미지가 **아직 VRAM에 머물러 있을 때** GPU를 강제하여 이미지를 256x192로 축소시키기 때문입니다. 마침내 `getImageData`가 호출될 때는 오직 196KB의 아주 작은 페이로드만이 PCIe 버스를 타고 넘어옵니다.

### 진솔한 결론
최신 컴퓨터에서 CPU는 8MB 배열 따위에 "질식"하지 않습니다. 하지만 `encoder.html`의 아키텍처 선택은 여전히 압도적으로 우수한 엔지니어링 결정입니다. 이 방식이 우수한 이유는 최신 CPU의 성능이 부족해서가 아닙니다. 브라우저 생태계의 아키텍처적 특성을 완벽하게 이해하고 활용했기 때문입니다: **가장 비용이 큰 CPU-GPU 동기화를 최소화하고, 무거운 픽셀 처리 작업을 원래 그 목적에 맞게 설계된 하드웨어(GPU)에 그대로 유지시킵니다.**
